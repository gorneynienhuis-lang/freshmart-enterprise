# 数据库与媒体成套备份、隔离恢复

本程序的媒体不在数据库中。只保存 SQL 会丢失商品公图、售后私图、评价原图和经明确同意发布的评价公图。完整恢复单位是一个经过认证的 bundle，不能任意拼接不同时间的 SQL 与图片卷。

本机脚本：`scripts/demo-backup.py`。Compose 入口：`scripts/deploy-public.py backup/restore`。当前优先验收本机隔离恢复；Docker/Railway 的实际云资源和传输尚未执行。最终结果以实际验收记录为准，以下命令存在不等于恢复成功。

## 一个 bundle 包含什么

目录权限 0700，四个文件均为 0600：

| 文件 | 内容 |
| --- | --- |
| `database.sql.gz` | 当前应用 schema 的结构与全部数据，不含 `CREATE DATABASE`、`USE`、数据库账户或全局授权 |
| `media.tar.gz` | `product/`、`private/`、`review-public/` 的已登记 raster 文件，保留严格的三类隔离 |
| `manifest.json` | 逐表数量、Flyway 版本/校验值、媒体数据库引用、逐文件长度/SHA-256、SQL 压缩前后 SHA-256、应用源码/JAR或镜像版本标记、采集一致性方式 |
| `manifest.hmac` | 对原始 manifest 字节的 HMAC-SHA256，防止只改清单再伪造普通 checksum |

认证密钥**在 bundle 外面**：本机 `.runtime/backup-integrity.key`，Compose `deploy/private/backup-integrity.key`，随机 32 字节、0600。首次备份生成，之后保留；恢复必须带原密钥。把密钥另行保存在私有备份位置，不能放入 bundle 或 Git；换一把新密钥无法验证旧备份。文件权限/HMAC不等于加密，SQL 中仍有账户散列、会话与业务数据，不公开上传这些文件。

备份要求所有应用写入进程停止，再使用持续持有的 MySQL 全局读锁覆盖“元数据、SQL、媒体复制、完成复核”整个采集过程。不是把 `--single-transaction` 当成数据库与文件系统之间的共同事务。当前仅支持本项目 InnoDB 基表；遇视图、存储过程、触发器、事件、非 READY 图片或未知文件立即拒绝，交给人工检查，不擅自清理。

备份与恢复都会拒绝：缺图、多图、重复媒体引用、大小/hash不符、临时未知文件、符号链接/硬链接、归档路径穿越、重复归档成员、异常媒体用途、丢失/修改的清单，以及错误认证密钥。解析归档时逐文件验证并手动写入，未使用 `extractall`。已存在的目标文件不覆盖，失败留下私有隔离目录和新 schema 供检查，不回头删除源数据。

## 本机完整演练

先只读检查，不停服务、不生成一致性备份：

```sh
python3 scripts/demo-backup.py inspect
python3 -m unittest discover -s scripts/tests -p 'test_backup*.py' -v
```

预留独占维护窗口后才执行：

```sh
python3 scripts/demo-backup.py backup --pause-backend --output .runtime/backups/替换为本轮唯一编号
python3 scripts/demo-backup.py verify .runtime/backups/替换为本轮唯一编号
```

`--pause-backend` 只对 `demo-runtime.py` 记录且当前进程身份吻合的后端发送正常停止信号。MySQL、Vite 均保持原状态。只有原先正在运行的后端才会在 `finally` 中用现有 JAR 恢复；不构建、不导入种子、不重置密码、不启动原来没运行的服务。若停止/启动失败，脚本明确报错，不强杀或猜测进程身份。没有该开关而后端运行时会拒绝备份。

显式选择全新 schema、全新恢复目录及其 `media/` 子目录，端口不得使用 3306/5173/8080：

```sh
python3 scripts/demo-backup.py restore .runtime/backups/替换为本轮唯一编号 \
  --schema fresh_mall_restore_替换为小写唯一编号 \
  --confirm-isolated-schema fresh_mall_restore_替换为小写唯一编号 \
  --recovery-directory .runtime/recoveries/替换为本轮唯一编号 \
  --media-directory .runtime/recoveries/替换为本轮唯一编号/media \
  --port 18080
```

schema 名只允许 `fresh_mall_restore_` 加 6–45 位小写字母/数字/下划线；命令中的中文占位必须替换。已存在 schema 即使空库也拒绝。本机恢复前会先认证并读取验证所有 SQL/图片字节，然后创建隔离目标。恢复完成会核对逐表行数、完整媒体引用、Flyway 记录，并重新导出恢复库，要求解压后的 SQL SHA-256 与原快照完全一致。

恢复新建独立、仅限目标字面 schema 的应用数据库用户及随机密码，SQL 重放也使用此受限用户，代码拒绝用 root 重放。数据库级 GRANT 对 schema 中下划线显式转义，避免被当成通配；参见 [MySQL 官方 GRANT 说明](https://dev.mysql.com/doc/refman/8.4/en/grant.html)。恢复生成独立 token/沙箱签名密钥；主库、主数据库用户和 `.runtime/demo.env` 均不改动。原业务账户密码散列来自 SQL。新的签名密钥有意使旧的 bearer/refresh 签名失效，旧会话不能直接冒充恢复后的登录。独立配置、SQL和日志均在该私有恢复目录，不写 Git。

只有数据库/媒体完整验证成功才允许启动测试后端；JAR 的 SHA-256 须与本机备份时一致：

```sh
python3 scripts/demo-backup.py start-recovery --recovery-directory .runtime/recoveries/替换为本轮唯一编号
python3 scripts/demo-backup.py verify-http --recovery-directory .runtime/recoveries/替换为本轮唯一编号
python3 scripts/demo-backup.py stop-recovery --recovery-directory .runtime/recoveries/替换为本轮唯一编号
```

测试后端仅监听 `127.0.0.1:18080`，使用独立 schema、媒体、进程记录和准确 Origin；不改当前 8080/5173 的主应用。恢复后的正常后台作业、测试登录与签发私图访问的审计只写隔离库。`stop-recovery` 核对 PID、启动时间、完整命令身份、专用端口与媒体目录后才正常停止，不删除恢复数据。

`verify-http` 要求快照实际含三类媒体和已经分派给合成客服的售后证据，不能临时在恢复库伪造“已经恢复”的文件。它验证公开商品图、评价公图的实际像素 SHA，匿名/无关会员对私图的 401/404、已分派 SERVICE 的会话绑定签名访问、私图 SHA 与 `no-store`，以及签名不能被另一主体复用。测试只在内存读取本机合成账号密码，不输出 token/密码/签名。若当前种子密码已变更或快照没有相应合成资料，应准备真实合成测试资料后重新备份，不擅自重置账户。

## Compose：成套捕获与新目标恢复

仅在已部署且镜像 digest 已锁定的目标机上执行：

```sh
python3 scripts/deploy-public.py backup --pause-application
```

脚本检查 Compose project/service 标签与容器身份，记录原来运行的 web/backend，只暂停它们；数据库保持原状态。停机后取得读锁，导出 SQL，再从停止的后端容器复制 `/app/media` 持久卷内容，与数据库引用完整比对。最终只恢复原来运行的容器；不改变 `restart: unless-stopped` 或启动原来停止的服务。依据 [Docker 官方说明](https://docs.docker.com/reference/cli/docker/container/cp/)，`docker cp` 支持停止的容器；脚本不使用 `-L`，复制后仍独立拒绝链接和未知条目。

恢复入口只创建同一个受管数据库服务器上的**全新隔离 schema**和本机空恢复媒体目录；不会停止原服务、覆盖原 `fresh_mall`、改主用户密码或换主卷：

```sh
python3 scripts/deploy-public.py restore deploy/backups/替换为bundle目录 \
  --schema fresh_mall_restore_替换为小写唯一编号 \
  --confirm-isolated-schema fresh_mall_restore_替换为小写唯一编号 \
  --recovery-directory deploy/recoveries/替换为本轮唯一编号 \
  --media-directory deploy/recoveries/替换为本轮唯一编号/media
```

它完成数据库/文件及 SQL 往返比对后保留独立新数据库凭据，状态为 `RESTORED_DATABASE_MEDIA_VERIFIED_NOT_STARTED`。新恢复容器、独立媒体挂载权限、独立域名/Origin与实际图片权限验证仍需目标平台完成；脚本不自动把恢复数据切成公网主系统。当前环境无 Docker，因此这两条 Compose 运行路径**尚未执行**，不能用本机恢复结果宣称容器恢复已通过。

## Railway：明确未执行边界

MySQL 服务与应用媒体卷是两个数据源，平台单独的 MySQL Backups 不能视为整套应用备份。当前 `--transport railway` 的 backup/restore 均直接拒绝，绝不输出“完整备份成功”。尚未授权创建云资源，未验证 Railway SSH/卷文件传输或恢复，不提供猜测可运行的停机命令。

目标平台实际接入时须先验证：应用及所有后台写入进入维护/停止状态；数据库快照/逻辑导出期间保持明确的只读点；同一维护点导出 `/app/media` 三类文件；导出数据库媒体引用、逐表计数和 Flyway/镜像标记；到私有传输目录验证缺图/多图/hash并使用本格式认证封装；在全新项目/schema和空媒体卷上实际启动验证，最后才决定切换。媒体卷挂载/SSH在停止应用时是否可用，必须在真实平台核实；不能把两个不同时间的原生卷备份直接拼成一致快照。

MySQL 一致性选项及 DDL 限制参考 [MySQL 8.4 官方 mysqldump 文档](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)。本方案刻意保留完整停写窗口，不声称热备、零停机、异地自动容灾或生产 SLA。

## 2026-10-18 已执行的本机结果

无秘密结果见 [backup-verification.json](backup-verification.json)。实际在 V001–V012 的本机 MySQL 8.4.11 上停应用采集：43 表、2632 行、7 媒体文件（product1/private4/review-public2）。恢复至全新 `fresh_mall_restore_formal_20261018_064037` 和独立私有媒体目录，逐表/Flyway/媒体均一致，重导出 SQL SHA-256 与原快照逐字节相同。

已实际启动 `127.0.0.1:18080` 独立后端，验证商品公图、评价公图实际像素及售后私图权限/签名主体绑定；恢复数据库账号读取主 schema 被拒绝。恢复进程随后正常停止，恢复库与私有文件保留。源8080健康UP、5173返回200，MySQL/Vite原进程保留。20项离线测试覆盖清单与归档攻击、目标保护、拒绝root重放和字面schema授权。

快照记录的是当时基线 Git commit 加**未提交工作树**，不是已经发布的干净版本；具体 commit、JAR SHA、迁移源码SHA及工作树标记保留在私有manifest，公开汇总保留非秘密版本信息。后续Git提交不能倒填成快照当时的版本。Docker/Compose运行、Linux容器恢复、Railway传输/恢复与公网部署仍未执行。

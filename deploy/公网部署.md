# 公网课程展示部署

2026-10-18。用户尚无服务器和域名，要求选操作最少的方式。**首选 Railway：一个 Java 应用服务同时提供已构建前端与 API，另加一个 MySQL 服务**。它提供平台域名与 HTTPS，可免去购买域名、管理 Linux/Caddy、跨域 Cookie 配置的步骤。这里是已经写入仓库的部署准备，不是“网站已上线”的声明。实际费用、账号授权和启用云服务留待用户确认后操作。

本项目是课程展示；支付、退差与退款均为沙箱，不能接收真实费用。数据库持久化、业务校验与角色权限正常运行。默认采用用户选择的 R03 主要页面；旧候选设计仍可回看。

## 首选：Railway 两服务

应用镜像见 `railway/Dockerfile`：在 Linux 中 `npm ci` 根据锁文件安装、执行前端 verify/build，再把 `dist` 放入 Spring Boot 静态资源，打包 Java 21 JAR。运行容器只有一个 Java 进程，前端与 `/api/v1` 同源，浏览器使用 Secure/HttpOnly Cookie。不要使用 Vite 开发服务器作为公网入口。`railway/railway.toml` 给出了构建路径、健康检查和单实例配置。

Railway 的 [官方 Dockerfile 文档](https://docs.railway.com/builds/dockerfiles) 说明自定义 Dockerfile 路径；[公网文档](https://docs.railway.com/networking/public-networking) 说明平台域名。我们采用固定 `8080`，同时设置 `PORT=8080` 与 `SERVER_PORT=8080`，生成域名时目标端口也选择 `8080`。[健康检查](https://docs.railway.com/deployments/healthchecks) 使用 `/actuator/health`；平台部署健康检查不等于持续监控或业务验收。

### 先建立空数据库，勿把 MySQL 大版本猜成 8.4

Railway 官方 [MySQL 说明](https://docs.railway.com/databases/mysql) 提供私网连接变量与持久卷。检查它创建的源镜像：截至本次查看，官方 [模板源清单](https://github.com/railwayapp-templates/template-marketplace/blob/main/storage/MySQL---mysql.md) 声明的是 `mysql:9`，`MYSQLUSER` 默认还是 root。**本仓库已经实测的是 MySQL 8.4.11，因此新建、尚未初始化的数据库服务应固定为 `mysql:8.4.11`，卷挂载 `/var/lib/mysql`，再首次启动。** 不要把已初始化的 9.x 数据卷直接切成 8.4；那是数据库降级，会破坏兼容性。修改模板镜像/数据库配置后，由我们负责该自定义配置的维护，不能把它称为平台替我们完成的数据库版本验收。

数据库服务命名 `MySQL`，不添加 Public Access/TCP Proxy。只给应用开公网域名。确认 MySQL 的持久卷存在，且当前版本真的为 `8.4.11`。若已有 9.x 数据，先保留并反馈，不通过删卷“解决”。

### 初始化流程

1. 在 Railway 建项目、MySQL 服务和连接本私有 GitHub 仓库的应用服务。应用构建上下文用仓库根目录，Config File Path 为 `/deploy/railway/railway.toml`，或在 Build Configuration 设置 Dockerfile Path 为 `deploy/railway/Dockerfile`。不要把 Root Directory 设为 `frontend/` 或 `backend/`，构建需要两边代码、设计资源与数据库迁移。
2. 给应用生成平台域名，记录准确的 `https://…up.railway.app`；尚未完成初始化前不分享网址。平台账户登录/付费/GitHub 仓库授权由用户确认后进行。
3. 在项目根目录生成独立云端配置（下面是占位域名，执行时替换成真实生成的网址）：

```sh
python3 scripts/deploy-public.py init --origin https://替换为实际域名 --email 替换为证书联系邮箱
python3 scripts/deploy-public.py check
```

4. 使用已登录并安装好的 Railway CLI。首次 SSH 可能要求在该平台登记 SSH 公钥，这是新增平台授权，需要用户确认。用明确的项目 ID，先通过数据库容器自身的 MySQL 客户端创建 `fresh_mall` 库和仅拥有该库权限的 `fresh_mall` 应用用户：

```sh
python3 scripts/deploy-public.py railway-bootstrap --project 替换为项目ID --service MySQL
```

脚本通过 [Railway SSH](https://docs.railway.com/cli/ssh) 传递 SQL，不打开数据库公网端口。root 密码仅在数据库容器内部从其原有环境读取，不出现在命令参数或公开日志中。若该库已有任何表，bootstrap 拒绝继续；不会改旧密码或覆盖已有数据。应用不使用 Railway 模板提供的 root 账户。

5. 把 `deploy/private/railway-app.env` 内容直接粘贴到 **应用服务私有 Variables/Raw Editor**，不要粘贴到聊天、Issue、仓库或截图。该文件包含随机应用数据库密码、JWT/沙箱密钥，以及精确的 APP_ALLOWED_ORIGINS。`MySQL` 服务名如改过，要同步修改文件中的 `${{MySQL.MYSQLHOST}}` 和 `${{MySQL.MYSQLPORT}}` 引用。DB_URL 使用私网域名，不能使用 MYSQL_PUBLIC_URL。其中固定的 `SPRING_PROFILES_ACTIVE=showcase` 是课程沙箱配置，勿改成 `prod`/`production` 来强行打开沙箱支付。
6. 部署应用，确认 Flyway 成功执行本提交中的全部 `database/migrations/*.sql`，包括员工治理迁移，健康状态 UP。JAR 自动包含这些迁移，**不要再把建表脚本手工执行第二次**。Maven Docker 构建跳过后端测试以避免把发布构建当成验收；测试必须在对应发布提交另行完成并保留证据。
7. 暂停对外分享、保持初始化窗口内无人注册/下单，向空业务库一次导入种子：

```sh
python3 scripts/deploy-public.py seed --transport railway --project 替换为项目ID --service MySQL
```

8. 初次登录各工作账号并修改密码，完成下列公网验收后再把网址发给老师/同学。云端账号与本机 Demo 密码彼此独立，不导入本机真实订单、地址、会话或数据库文件。

### 应用变量

`init` 会生成完整私有文件，此表只解释用途，不提供通用密码：

| 变量 | 配置 |
|---|---|
| `RAILWAY_DOCKERFILE_PATH` | `deploy/railway/Dockerfile` |
| `SPRING_PROFILES_ACTIVE` | `showcase` |
| `SERVER_ADDRESS` / `SERVER_PORT` / `PORT` | `0.0.0.0` / `8080` / `8080` |
| `DB_URL` | 私网 `jdbc:mysql://…:3306/fresh_mall`，UTC、READ-COMMITTED 使用应用配置 |
| `DB_USERNAME` | `fresh_mall`，仅该库权限 |
| `DB_PASSWORD` | 本次 init 独立随机密码 |
| `APP_TOKEN_SECRET` / `SANDBOX_SECRET` | 分别独立随机 32 字节以上，重启保留 |
| `APP_ALLOWED_ORIGINS` | 唯一准确的 `https://实际域名`，无尾部路径、逗号、通配符 |
| `APP_PUBLIC_ORIGIN` | 与唯一允许的 HTTPS 商城 origin 相同 |
| `APP_MEDIA_DIR` | `/app/media`，应用服务单独挂载持久卷 |
| `RAILWAY_RUN_UID` | `0`，入口脚本仅初始化卷后降到 UID 10001 |
| `APP_SECURE_COOKIES` | `true` |

MySQL 只使用平台内部网络。数据库与应用图片均必须有独立持久卷：应用挂载 `/app/media`，配置 `APP_MEDIA_DIR=/app/media`、`APP_PUBLIC_ORIGIN=https://实际域名`。依据 [Railway 卷权限说明](https://docs.railway.com/volumes)，应用设 `RAILWAY_RUN_UID=0` 让入口脚本初始化挂载目录权限，随后以 UID 10001 启动 Java。不能只把媒体写进容器临时层。该路径仍待实际云构建与重启保留验证。应用日志保留在平台，里面可能含业务信息，不能整份公开。不要通过改密码环境变量来轮换已经初始化的数据库账户，必须走明确的数据库密码变更流程。

### 费用与最终待确认事项

用户希望别人输入或点击网址即可进入，网址能自选更好。优先使用不另收域名费用的`*.up.railway.app`平台域名。根据[官方CLI说明](https://docs.railway.com/cli/domain)，平台域名可以重命名前缀；例如`dhu-freshmart.up.railway.app`只是尚未申请的示例，是否可用需实际创建时核验，不假称已占用成功。先确定平台域名，再执行init生成精确Origin、Cookie与素材地址配置；不自动购买独立域名。平台域名免费不等于应用/MySQL运行免费。直接访问不依赖搜索引擎收录，按商城名称被搜索到不是上线验收的前提。

根据 [Railway 官方价格](https://railway.com/pricing) 和 [套餐说明](https://docs.railway.com/pricing/plans)，Hobby 最低 **5 美元/月**，含等额资源用量；实际计算、内存、存储与流量超出部分继续计费，**5 美元不是月费上限**。Java 和 MySQL 都是持续运行的服务，不能保证落在 5 美元以内。正式创建前需用户确认付费方式、允许的预算和保留时长；在平台设置相应的费用控制，并说明达到硬限制可能停止服务。账号/信用卡未授权前不创建收费资源。

仍需目标平台实际核实：最终域名、地区、MySQL 镜像/存储、资源用量、构建与健康检查、外网浏览器登录和账户权限、备份恢复。当前没有生成真实公网网址。

## 账号分配与交付

`init` 每角色生成不同随机初始密码，使用现有 PBKDF2-SHA256/600000 次散列，SQL 只有散列。仅写入七个合成标识 `13800000001`–`13800000007`；不是实际收短信号码，不联系任何号码。

| 登录标识 | 角色 | 谁使用 |
|---|---|---|
| `13800000001` | MEMBER | 普通购物演示；也可自行注册会员 |
| `13800000002` | PICKER | 拣货与实重确认 |
| `13800000003` | COURIER | 配送与签收 |
| `13800000004` | SERVICE | 售后审核 |
| `13800000005` | FINANCE | 独立执行退款 |
| `13800000006` | OPERATOR | 运营工作台 |
| `13800000007` | ADMIN | 人员账号与权限管理 |

首页右上角使用统一登录；员工登录后进入工作台。账号初始均要求首次改密，变更后需重新登录。ADMIN 不自动变成财务、客服或配送员；同一笔售后的审核与退款执行需要不同人员。管理员密码只交给用户，不能放在公开课程仓库或页面。可以给老师专门分配受控账号，不把主管理员密码发给所有人。

密码文件在 `deploy/private/accounts.txt`，目录权限 0700，文件 0600。仅显式运行以下命令才显示密码，请在私人终端查看，避免录屏：

```sh
python3 scripts/deploy-public.py credentials
```

`deploy/.env` 是非秘密域名与版本配置；`private/`、`.env`、备份均被 Git 忽略，Docker 构建上下文也排除私有数据。应用运行变量由平台/容器宿主管理员可见，不能把“没有进 Git”误写为“宿主管理员也无法看到”。

种子只在空业务库执行。导入事务最后写唯一安装审计标记；相同安装再次执行只报告已存在，不重置密码、库存、券和订单。有业务数据而没有该安装标记时拒绝导入。库表/权限由 Flyway 与初始化步骤分别处理，seed 不负责清库。正常库存会随时间过期（当前课程种子正常批次约 8 天、临期约 2 天），不会每天重置日期伪造补货；长期展示须走真实的库存维护/补货功能。

## 备份、恢复与版本回退

恢复单位必须同时包含数据库与应用媒体卷。Railway 单独的 MySQL Backups 不包含商品图、售后私图和评价公图，不能称作完整备份。具体平台维护、导出/传输与恢复仍待真实部署时验证；当前 Railway backup/restore 自动入口直接拒绝，不凭此文宣称完成。完整格式、本机实际隔离演练步骤与平台边界见 [备份恢复.md](备份恢复.md)。

GitHub tag 固定每版源码。应用版本回退与数据库回退是不同操作：Flyway 迁移可能只向前兼容，未确认兼容时不能只点旧镜像。保留数据库备份、发布提交、镜像 digest 与私有配置的离线副本；不要销毁数据库卷、删除项目后再声称可以直接回滚。

## 可移植备选：已有 Linux 服务器时用 Compose

仓库保留 `compose.yaml`、两个 Dockerfile 与 Caddyfile，适合日后已有 Linux 服务器/域名时迁移。公网只开 Caddy 80/443；MySQL、后端和内部健康端口均不映射到宿主公网。Caddy [自动 HTTPS](https://caddyserver.com/docs/automatic-https) 要求正确 DNS 与可达的验证端口；前端静态文件、API 与图片由同一域名访问。Compose 的 [service_healthy 依赖](https://docs.docker.com/compose/how-tos/startup-order/) 只解决启动顺序，不代替业务验收。

Linux 目标机先安装 Docker Engine、Compose v2、Python3、Git，准备域名和服务器防火墙。内存建议预留 4GB 作为课程项目启动基线；这不是已测得的容量或性能承诺。然后从已审阅且已提交的源码执行：

```sh
python3 scripts/deploy-public.py init --origin https://替换为实际域名 --email 替换为证书联系邮箱
python3 scripts/deploy-public.py lock-images
python3 scripts/deploy-public.py up
python3 scripts/deploy-public.py status
```

`lock-images` 拉取明确补丁版本，再记录镜像不可变 digest；`up` 拒绝未锁定镜像与未提交的 tracked 修改，构建完成后验证 Caddy、启动 DB/后端、导入一次种子，最后开放 Web。构建通过不表示公网 TLS、Cookie 或业务检查通过。MySQL root 只供初始化与备份，后端以非 root 的容器用户运行，数据库应用账户只有 `fresh_mall.*` 权限；容器有只读根文件系统/独立 tmpfs。

Compose 成套备份（需独占维护窗口）：

```sh
python3 scripts/deploy-public.py backup --pause-application
```

输出 `deploy/backups/fresh-mall-时间/`，包含数据库、三类媒体和外置密钥认证的清单；目录0700/文件0600。应用停止写入，并用全局读锁覆盖 SQL 与媒体复制。恢复仅接受从未存在的隔离 schema，不会自动 DROP/删卷：

```sh
python3 scripts/deploy-public.py restore deploy/backups/替换为bundle目录 \
  --schema fresh_mall_restore_替换为小写唯一编号 \
  --confirm-isolated-schema fresh_mall_restore_替换为小写唯一编号 \
  --recovery-directory deploy/recoveries/替换为本轮唯一编号 \
  --media-directory deploy/recoveries/替换为本轮唯一编号/media
```

恢复不停止主 Web/后端，只写明确指定的新 schema 与空目录；重导出 SQL 的 SHA、行数、媒体引用、Flyway 均须匹配。它不自动切换主系统；独立恢复容器、挂载与 HTTP 图片权限仍需在目标机实际验证。本机恢复使用 `scripts/demo-backup.py`，不以 `fresh_mall_demo` 为恢复目标。

## 发布前实际验收（尚待目标平台执行）

- 从另一网络访问 HTTPS，首页/列表/详情/素材完整，手机也能打开；无 mixed-content、错误图片域名或 404。

- 在隔离环境实际恢复备份，核对业务数据及版本；记录最终部署提交、URL、测试时间和结果。

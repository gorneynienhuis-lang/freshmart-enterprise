# MySQL 退款故障隔离演练草稿

脚本 `scripts/e2e-refund-recovery.mjs` 仅做过 `node --check`，尚未执行业务。不得把此说明作为演练通过证据。主演示服务8080与商城5173均不用于此测试。

由主代理建立一套迁移到V013的 MySQL8.4隔离库及后端，指定 loopback18081、显式test/demo、故障开关true、独立密钥和本库凭据。演练建议 maxAttempts3、base1秒、max2秒、lease30秒；此处是演练配置，部署默认仍5/10/300/30。先关闭 commerce jobs，待 prepare 完成后仅重启隔离后端开启jobs；不要重启共享主服务。`app.allowed-origins` 要允许该隔离后端精确origin。

私有配置为0600 JSON，保存于 `.runtime`，字段为：

```json
{
  "purpose": "engineering-refund-recovery",
  "baseUrl": "http://127.0.0.1:18081",
  "schema": "fresh_mall_restore_engineering_UNIQUE",
  "mysqlBinary": "/absolute/path/to/mysql",
  "mysqlDefaultsFile": "/absolute/path/to/private-client.cnf",
  "finance": {"phone": "PRIVATE_SEED_PHONE", "password": "PRIVATE_SEED_PASSWORD"},
  "maxAttempts": 3,
  "jobsDisabledForPrepare": true
}
```

schema只接受 `fresh_mall_restore_engineering_` 或 `fresh_mall_refund_recovery_` 加至少5位唯一后缀；purpose必须完全匹配。端口仅允许18080至18999的loopback。脚本不会创建、恢复、删除数据库或启停任何进程。配置和生成的合成账号仅保存在 `.runtime/refund-recovery/<schema>`。重复prepare拒绝覆盖本库已建立的私有state，避免重复下单。

HTTP三阶段分别用环境变量选择阶段，不能把阶段作为位置参数（契约验证器的位置参数用于契约文件）：

```sh
REFUND_RECOVERY_PHASE=prepare REFUND_RECOVERY_CONFIG=/absolute/private/config.json node scripts/e2e-refund-recovery.mjs
# 主代理此时仅重启隔离后端，开启jobs
REFUND_RECOVERY_PHASE=verify REFUND_RECOVERY_CONFIG=/absolute/private/config.json node scripts/e2e-refund-recovery.mjs
REFUND_RECOVERY_PHASE=cleanup REFUND_RECOVERY_CONFIG=/absolute/private/config.json node scripts/e2e-refund-recovery.mjs
```

prepare通过真实API注册本轮合成会员、创建地址，从真实可售商品下单/支付/取消四笔订单。退款由合法取消流程产生。随后只对这四个原退款号的私有fault计划写SQL，分别注入临时超时、明确拒绝、渠道提交后丢ACK，以及另一次保留给UI的明确拒绝。它不会设置订单/支付/退款/任务状态，也不会改金额或伪造FAILED。

verify观察实际MySQL任务与账本结果，临时超时和明确拒绝必须达到FAILED/DEAD并保留资金预留；丢ACK必须存在唯一成功回执并只记账一次。随后验证会员403、财务旧版本409、财务原退款号恢复和共享幂等重放，并检查原executor审计。所有HTTP响应逐条校验机器契约，证据只记录路径/状态/traceId和白名单账务快照，不写响应中的密码、token或收货信息。

cleanup当前为只读收尾核对：四订单均CANCELED、原退款均SUCCESS、唯一渠道回执、outbox COMPLETED、预留为0。保留合成业务和审计，不删除历史。若verify失败，阶段结果保留FAIL与pendingCleanup；不得通过SQL设置SUCCESS、重置尝试数或重复未知写入来“修绿”。由主代理按当前真实状态决定下一步。

输出为 `docs/evidence/refund-recovery-v022/<runId>/<phase>-<timestamp>.json`，每次独立文件，失败不覆盖。浏览器界面的FAILED正向按钮验证另开隔离Vite15173窗口，当前HTTP脚本不声称完成UI证据。


第四笔 `ui-retry` 在HTTP verify中只确认真实FAILED/DEAD、无receipt且预留守恒，然后标记 `pendingUi`，不经HTTP恢复。这样监控可以采集真实DEAD窗口，随后在隔离Vite15173中验收实际按钮。私有配置额外添加 `uiBaseUrl` 为 `http://127.0.0.1:15173`，且其后端必须为18081；由root启动此隔离代理，不使用5173。

```sh
REFUND_RECOVERY_CONFIG=/absolute/private/config.json node frontend/scripts/e2e-refund-retry.mjs
# UI通过后才执行HTTP cleanup
```

UI脚本先在FAILED筛选的真实分页中找原refundId，验证UI代理能读取本库独有合成订单，避免误连主后端；用真实logout撤销仅该浏览器登录会话，再由仍打开的旧弹窗提交，验证401只发送一次、控件禁用、任务/资金不变。重新登录后由独立FINANCE填写原因、明确提交同原退款号；等待渠道成功，再刷新并跨SUCCESS真实分页找该记录，确认按钮消失。SQL只读核对退款号/支付号未换、唯一完整回执、资金预留0和唯一恢复审计。分别截图1440/1024/390，登录手机号/密码框遮罩，并记录真实schema/JS/缺图/溢出结果。不会拦截路由伪造响应，也不会对错误或未知结果自动重发。

首次UI验收脚本已按真实401跳转行为修正：旧退款弹窗被移除并转登录，不应继续等待不存在的旧按钮禁用。修正后的独占窗口已实际通过，原FAIL保留。输出为同runId下独立 `ui-<timestamp>/result.json` 和截图；HTTP cleanup要求 `uiVerified=true` 且不再有pendingUi，不能跳过。


实际结果已补入 `docs/evidence/refund-recovery-v022/README.md`：prepare31、verify16、最终UI43、cleanup8条真实契约响应均0 schema错误；12张三宽截图、0JS/缺图/外溢。四笔原退款均SUCCESS且单回执、预留0。socket零API预检FAIL和UI错误等待旧弹窗的首轮FAIL均保留，不能以最终PASS覆盖。

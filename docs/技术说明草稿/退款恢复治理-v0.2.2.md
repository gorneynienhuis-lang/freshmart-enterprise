# 退款恢复与故障边界（源码草稿，测试待执行）

本轮没有新增公开故障接口或改变退款金额。原 `POST /admin/refunds/{id}/retry` 用于独立财务恢复同一个原退款号，仍由共享幂等命令事务、当前角色、会话、资源版本与原因约束；原审核人、购买人不能自行恢复。售后原审批关联必须有效。后台原执行入口保持异步，不在请求中绕过工作任务直接完成账本。

## 渠道事实与本地账本

`SandboxRefundReceiptStore.record` 是独立 Spring Bean 的 `REQUIRES_NEW` 事务。在锁住订单、支付、退款、任务与执行人并核验当前授权后，模拟渠道把原退款号、支付号、金额、渠道退款号、完成时间作为不可变成功凭证提交。Gateway 在事务外返回，因而“渠道成功、响应丢失”会留下真实可查回执，不会随异常回滚。

工作线程先查询并验证完整回执。已存在的合法成功事实不再发起新退款，即便原财务人员之后撤权，本地账本也必须按事实补记。账本更新、预留转已退、退款成功、任务完成以及售后汇总在同一事务内提交。订单/支付/退款的版本增量遵循安全整数上界。该演示渠道不是实际银行或支付公司；真实支付接入仍需替换适配器及验证其签名和查询接口。

## 租约和退避

V013 给 outbox 增加内部 `lease_token`、递增 `lease_generation`、本恢复周期尝试数 `cycle_attempt_count` 和 `failed_at`。现有 `attempt_count` 保留为累计尝试数，`created_at` 永不重置。领取任务同时检查 `available_at`、租约到期、状态和旧代数，发放随机令牌。完成/失败的写入必须携带原 claim，并使用令牌、代数、PROCESSING 和未过期时间做数据库 CAS；过期线程不能清空新线程租约或记账。

默认自动周期最多 5 次，基准 10 秒、上限 300 秒，退避 `min(max, base * 2^(attempt-1))`，租约 30 秒；配置有界且启动校验。由于崩溃不能知道最后发送结果，失租后始终先查成功回执；无成功事实且预算耗尽，停止再次发送。永久拒绝、回执不一致或执行人撤权同样进入 DEAD，退款 FAILED。失败不会释放或重复增加 `payment.refund_reserved`，避免其他申请占用已承诺的退款资金。

独立财务恢复仅将原 DEAD 任务重新置为 PENDING、重置本周期计数并失效旧令牌，保留累计尝试和原业务键。原 reviewer 不变；恢复前 executor 和 reviewer 记入审计 before，恢复人及新 executor 记入 after。身份、密码、令牌和渠道原始报文均不进入审计。

## 私有故障演练

默认 `app.sandbox-refund-faults-enabled=false`。只有显式开启的 demo/test 且 `server.address` 为 loopback 才能启动；showcase/prod/production、公开绑定或未启用沙箱均拒绝。无 HTTP 控制路由。受控测试按原退款号配置私有数据库计划：

- `TRANSIENT_BEFORE_COMMIT`：提交渠道成功凭证前超时，验证退避与耗尽。
- `REJECT_BEFORE_COMMIT`：渠道明确拒绝，验证 DEAD 与财务原号恢复。
- `ACK_LOST_AFTER_COMMIT`：渠道凭证提交后丢失响应，验证一次补账、撤权后仍按事实记账。

故障计数消费另用 `REQUIRES_NEW`，在事务外抛固定错误，保证失败后不会回滚计数而永久重复注入。同一任务的生产状态不能由测试 SQL 伪造；整合测试通过真实 quote→订单→支付→取消→渠道故障产生 FAILED。回执绑定损坏测试明确属于数据完整性攻击测试，不能作为正常故障成功证据。

## 验证状态

新增 `RefundRecoveryIntegrationTest`，覆盖退避/DEAD/资金守恒、原号恢复审计、丢 ACK、崩溃失租、撤权门禁、旧线程 fencing、并发抢占、当前会话与版本、缺失 outbox 拒绝伪成功、绑定不符、HTTP 幂等与未知金额字段、公开投影不泄漏租约、配置边界。既有 commerce/aftersale/finance/media/support 测试改为携带真实 claim。测试尚未运行；由主代理串行编译/执行，主运行库未修改。隔离 MySQL 故障演练和运行截图仍待主代理提供独占窗口。

补充只读审查修正：退款工作入口与渠道回执独立事务明确使用 READ_COMMITTED；同时用户、会话、角色、原审批、回执、退款汇总与售后已退明细均使用当前锁读，避免外层 REPEATABLE_READ 加入时内部隔离注解无效。MyBatis 对这些当前读同时清理会话缓存。特别是售后明细若仍读旧 `refunded_amount`，第二笔补账会重复增加订单行退款，所以退款集合与明细必须一同锁定并读取当前值。新增外层旧快照等待同单 order 锁、多支付退款最终汇总测试，以及两项旧快照下撤销角色/会话的并发测试；仍待统一测试执行。

该选择依据 MySQL 官方对[事务隔离级别](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)与[锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)的说明：REPEATABLE_READ 普通查询保留先前快照；授权和资金当前状态需要锁定读，不能把“等到了用户锁”误当普通查询自动刷新快照。

测试诊断边界（2026-10-18）：主代理旧副本的 targeted 44项出现0failure/1error，错误是 H2 在旧RR快照下锁已撤销会话时主动报 SQLSTATE40001；该诊断不能视为新源码通过。新测试只允许明确401拒绝或 `TransientDataAccessException` 原因链40001安全回滚，随后核对退款/资金/outbox全部未变；不吞其他异常、不重发恢复命令。此外售后完成的订单快照使用父退款事务已推进的版本，不再重复加一；售后版本到上界返回409并回滚本地任务/资金/明细，保留已提交渠道回执。对应两项边界测试也已补齐，仍等待主代理新副本验证。
